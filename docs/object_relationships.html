BBA 模型对象关系与数据流梳理

1. 核心对象概览

在 GroupLifecycleSimulationService 中，主要涉及以下几个关键对象，它们分别承担不同的职责：

PolicyContract (Entity)
职责： 数据库实体类，映射 zh.t_pp_jl_contract 表。
生命周期： 仅在初始化阶段使用，用于加载原始保单数据。
GroupCohortState (Model)
职责： 维护整个合同组（Group）的长期状态。
包含： List<GroupPolicyState>，以及组级别的期初/期末余额（BOP/EOP CSM, LC等）。
生命周期： 贯穿整个仿真过程，跨年度持久存在。
GroupPolicyState (Model)
职责： 维护单张保单在组内的长期状态。继承自 PolicyState。
包含： 保单基本信息、期初余额 (BOP)、期末余额等。
生命周期： 贯穿整个仿真过程，每年更新。
CalculationContext (Context)
职责： "上帝对象"，承载单次计算（单张保单、单年度）所需的所有上下文信息、中间变量和结果。
包含： 引用 PolicyContract (或其数据)、PV数据、利率曲线、精算假设、计算过程中的各种中间值（如利息、变动额、分摊结果）。
生命周期： 每年、每张保单创建一个新的实例。
PolicyContextInput (DTO)
职责： 数据传输对象。仅用于将 CalculationContext 中的关键数据提取出来，传递给 GroupCsmLcMeasurementService 进行组级别聚合计算。
生命周期： 瞬态，仅在组级别计算前创建，计算后丢弃。
GroupStatusResult (DTO)
职责： 封装组级别状态判定的结果。
包含： 组是否盈利 (isProfitable)、Net Trial 值、聚合后的 CSM/LC 余额。

2. 字段赋值流程与数据流转

数据在各对象间流转的典型路径如下：

Database → PolicyContract → GroupPolicyState → CalculationContext → PolicyContextInput → GroupStatusResult → CalculationContext → GroupPolicyState

详细步骤解析

步骤 1: 初始化 (Initialization)

源： PolicyContract (DB)
目标： GroupPolicyState

在 initializeGroup 方法中，将数据库实体转换为内存中的状态对象。

  • PolicyContract.policyNo → GroupPolicyState.policyNo
  • PolicyContract.startDate → GroupPolicyState.startDate
  • ... 其他基本信息
  • 初始化 BOP (Beginning of Period) 值为 0。

步骤 2: 年度计算准备 (Per Year Loop)

源： GroupPolicyState
目标： CalculationContext

在 simulateLifecycle 循环内部，为每张保单创建计算上下文。

  • GroupPolicyState.policyNo → CalculationContext.policyNo
  • GroupPolicyState.bopCsm → CalculationContext.bopCsm (期初余额传递)
  • GroupPolicyState.bopLc → CalculationContext.bopLc
  • 加载外部数据：PV数据 (pvSourceData)、利率 (ratesDf)、假设 (assumptions) 注入到 Context。

步骤 3: 组级别汇总准备

源： CalculationContext
目标： PolicyContextInput

在单单计算部分完成后，GroupCsmLcMeasurementService.collectPolicyData 提取数据。

  • CalculationContext.unitId → PolicyContextInput.unitId
  • CalculationContext.bopCsm → PolicyContextInput.bopCsm
  • CalculationContext.nbInitialCsm → PolicyContextInput.nbInitialCsm
  • CalculationContext.ifInterestCsm → PolicyContextInput.ifInterestCsm (中间计算结果)
  • ... 其他用于判断盈利/亏损的字段

步骤 4: 组状态回写与分摊

源： GroupStatusResult / PolicyAllocationResult
目标： CalculationContext

GroupCsmLcMeasurementService.writeBackToContexts 将组级别计算结果（如吸收额、分摊额）写回 Context。

  • GroupStatusResult.isProfitable → CalculationContext.isProfitable (通过逻辑判断设置)
  • PolicyAllocationResult.csmAbsorbed → CalculationContext.csmAbsorbed
  • PolicyAllocationResult.allocatedGroupLc → CalculationContext.allocatedGroupLc

步骤 5: 年度结转 (End of Year)

源： CalculationContext
目标： GroupPolicyState

年度计算结束后，将期末值 (EOP) 更新回状态对象，作为下一年的期初值。

  • CalculationContext.endCsmFinal → GroupPolicyState.bopCsm
  • CalculationContext.endLcFinal → GroupPolicyState.bopLc
  • CalculationContext.eopIacfBalance → GroupPolicyState.bopIacf

3. 易混淆点解析

1. CalculationContext vs PolicyContextInput

CalculationContext 包含所有信息，包括大对象（如 PV 数据 List）。PolicyContextInput 是一个轻量级 DTO，只包含数字字段（BigDecimal），专门用于组级别的高性能聚合计算，避免传递整个 Context。

2. UnitId 的构建

代码中使用 policyNo + certiNo 作为 unitId。必须确保在所有阶段（初始化、Context创建、DTO转换）使用完全一致的构建规则，否则在回写（WriteBack）阶段会匹配失败。

3. 两次 CSM/LC 计量调用

代码中存在 "Two-Pass" 计算逻辑：

  1. 第一次调用 csmLcMeasurementService：基于单单假设计算初步结果，用于汇总判断组状态。
  2. 第二次调用 csmLcMeasurementService：在得知组状态（盈利/亏损）和分摊吸收额后，重新计算最终的 CSM/LC。

混淆点： 中间变量会被覆盖或更新，需注意读取的时机。
